# Contributing
Use feature branches after the foundation commit. Open an issue describing an evidence gap, bug or resource proposal, then a pull request with focused changes and validation.

Code contributions must pass npm ci, npm test and npm run build. Add meaningful adapter/error-path tests where behavior changes. Include keyboard/accessibility checks for UI changes. Do not add mandatory telemetry, proprietary paid services, secrets, identifiable learner data, generated builds or node_modules.

Research/resource contributions need a real source URL and identifiers when available; publication metadata; source retrieval date; rights/attribution; population and method when claims are made; limitations/contradictions; a distinction between personal interpretation and source findings; and a conflict-of-interest disclosure. Link-only is preferable when redistribution rights are unclear. Do not invent citations or imply peer review.

Educators and researchers can suggest instructional adaptations, corrections and curated collections. Community feedback is not publication approval. A maintainer/editor must review source provenance, rights, accessibility and claim support before merging content. AI assistance must be disclosed with scope and human review. Be respectful; harassment and discriminatory content may be removed. Moderation decisions should give a documented reason and an appeal route through maintainers.

By contributing, you grant your authored code/documentation under MIT unless a file explicitly uses another approved license. Retain all third-party notices; never relicense linked publications. See EDITORIAL_POLICY.md. No unreviewed contribution is automatically published.
